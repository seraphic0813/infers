## 0. 要約(TL;DR)

- **何を足すか**: XAU/USD の M5 トレンドフォロー・スキャルピング。M15 の EMA50 を上位足
  バイアスに、M5 の EMA9/21 ゴールデン/デッドクロス + EMA21 押し目 + ATR/出来高フィルタ
  で成行参入する。高ボラティリティ環境適応型のトレンドフォロー。
- **執行の核**: 50/50分割。**TP1(0.5×ATR。v1.3 は 0.4×ATR)で半玉利確 → RUNNER**。
  残玉SLは同じ確定足のうちに建値を経て **「その足の高値(売りは安値)− 0.15×ATR」まで前進**し
  (= 建値 + 0.25×ATR 以上。§3「TP1到達足の実際のSL位置」)、以後 **0.15×ATR トレーリング +
  TP2(3.0×ATR)** で手仕舞い(v1.1確定値。§12)。
  v1.2ではさらに**相対ボラフロア(`atr_floor_bps=5.0`)**を追加採用(§15)、
  v1.3 で TP1 を 0.4×ATR に前倒し(プリセット `atr_trend_scalp_v13`。§18)。
- **半玉分割には最低2ステップ(0.02ロット)が必要**。`--risk-pct` 使用時は `--min-volume-steps 2`
  (CLI既定)で運用する。1にすると半玉が作れずバックテストと別の売買になる(§3)。
- **実装**: `strategies/atr_trend_scalp/`(`resample.py`=M5→M15 / `provider.py`=4条件ゲート /
  `execution.py`=`AtrTrendExecution` FSM / `signals.py`=`AtrTrendPlan`/`AtrTrendOutput` /
  `report.py`)+ レジストリ1件登録。**L0/L1 への新規追加は不要**(M5/M15/EMA/ATR/SMA は既存)。
- **AIゲート**: Narrow Focus 固有特徴量前提の既定ルールゲートは本手法の features を
  GUARDRAIL NO_GO にするため、**`--ai-client none`(パススルー)** で参入ゲートを無効化する
  (smc_bos/market_tpsl と同じ既知制約。防御層は別途全手法に強制され続ける)。

## 2. エントリー判定(本手法の正)

M5 確定足ごとに以下4条件がすべて成立し、かつ建玉ミラーがフラット
(+ `session_filter` 有効時は時間帯内)のとき、成行参入プランを1件出す。

### ロング(買建。ショートは全条件を対称に反転)
1. **上位足バイアス**: 直近確定 M15 終値 > EMA50(M15)。
2. **短期モメンタム**: EMA9 > EMA21(M5・ゴールデンクロス状態)。
3. **リトレース(押し目)**: 直近 `retrace_lookback`(既定3)本以内で安値が EMA21 を
   下回る/接触し、当足終値が EMA21 を回復(反発)している。
4. **ボラ&出来高フィルタ**: `ATR14 >= atr_vol_mult(1.1) × 直近20本平均ATR`
   **かつ** `volume >= vol_mult(1.6。v1.1 で 1.2→1.6) × 出来高SMA20`(ダマシ排除)。
5. **相対ボラフロア**(v1.2〜): `ATR14 / 終値 >= atr_floor_bps(5.0) bps`(=0.05%。値動きの小さすぎる相場を見送り。§15)。

- 参入参考価格 = 確定足終値(仕様書「次足始値で成行」の代理。SimBroker は確定足
  クローズ価格で約定)。**確定足主義**によりティック/形成中バーのヒゲでは判定しない。
- **平均ATR20** は直近20本(当足含む)のATRの単純平均。**出来高**は MT5 の tick_volume
  (XAUUSD CFD に真の出来高は無い。業界標準の代替指標)。

## 3. 出口・防御(`AtrTrendExecution` FSM / §A 準拠)

すべて **100%決定論の Python**(LLM非依存 §A-1)。状態は Enum 一本(§A-8):

```
IDLE ─place()─▶ OPEN(全玉・初期SL) ─TP1到達─▶ RUNNER(残玉・SL=高値−trail, trailトレール) ─TP2到達─▶ CLOSED
        │                                    │
        └── on_broker_event: SL_HIT ─────────┴──▶ CLOSED     close(): データ末尾/停止 ─▶ CLOSED
```

倍率はすべて**エントリー時の ATR14 で固定**(既定値は §7。v1.3 は TP1 のみ 0.4)。

- **初期SL**: `entry ∓ sl_atr_mult(1.0)×ATR`(min_stop_distance_ticks を下限にガード)。
  発注と同時にブローカー側の逆指値として設定(SLなしの状態は作らない。足の途中でも約定する)。
- **TP1(第1利確)**: 確定足の高値(売りは安値)が `entry ± tp1_atr_mult(0.5、v1.3 は 0.4)×ATR`
  に到達したら **半玉を成行で利確** → RUNNER。続けて残玉SLを建値(実約定価格)へ前進させる。
  `volume_steps` が1で半玉が作れない場合は部分利確を行わず、全量のまま RUNNER へ移る。
- **トレール**: RUNNER で毎確定足、`その足の高値(売りは安値) − 方向×round(trail_atr_mult(0.15)×ATR)`
  へSLを前進(**利益方向のみ**。A-3)。
- **TP2(第2利確)**: 確定足の高値(売りは安値)が `entry ± tp2_atr_mult(3.0)×ATR` に到達したら
  残玉を成行で全決済 → CLOSED。
- 半玉数は `--risk-pct` で volume がリサイズされ得るため**プランに焼き込まず**、`place()`
  時点の実 volume_steps から `half = volume // 2` を導出する(端数は残玉側へ寄せる)。

### TP1到達足の実際のSL位置(2026-11-15 明確化)
旧記述は「TP1 で残玉SLを建値へ移動」だったが、実装(`execution.py` `on_bar`)では TP1 を処理した
**同じ確定足のうちに RUNNER のトレール処理も続けて走る**。そのため残玉SLは建値で止まらず、
`その足の高値 − 0.15×ATR` まで前進する。TP1 到達足の高値は少なくとも `entry + tp1×ATR` なので、
残玉SLは **少なくとも `entry + (tp1 − trail)×ATR`**(v1.2: +0.35×ATR、v1.3: +0.25×ATR)になる。

例(買い・ATR=$4.00・entry=3,880.00・v1.3): TP1=3,881.60 に高値3,882.00の足で到達 →
半玉利確 → 残玉SLは 3,880.00(建値)を経て同じ足で 3,882.00 − 0.60 = **3,881.40** へ。
以後反落しても残玉は約 +$1.40 で決済され、損益ゼロ(建値撤退)にはならない(ギャップ・
スリッページ時を除く)。これは記述の不足であり実装の不具合ではない。バックテストの数値は
すべてこの実際の動きで計算されている。

### 最低ロットと半玉分割
`--risk-pct` のロット計算(`VolumeSizer`)は `残高 × risk_pct ÷ (SL距離 × 1ステップのティック価値)`
を切り捨てて `[min_volume_steps, 4]` に収める。`--risk-pct 0.0003`・残高$10,000・ATR≈$4 では
計算値が0になり、**実質的に常に最低ロット**になる(2ステップに自然に増えるのは残高約$27,600以上)。
バックテスト(CLI既定 `--min-volume-steps 2`)は 0.02ロットで「半玉利確+残玉トレール」を行う。
`--min-volume-steps 1` だと 0.01ロットで半玉が作れず、TP1 で利確せず全量がトレールに移る
**別の売買**になるため、ライブ/デモもバックテストと同じ `2` で運用する
(2026-11-15、デモ構成を 1→2 に是正)。

### 含み益トリガーの採用(A-4 手法契約)
本手法は **含み益トリガーの防御調整(TP1到達で建値化、その後トレール)を自手法の契約
として採用**する。CLAUDE.md §A-4 の手法スコープ化により許可される(Narrow Focus は
この自由を使わない)。判定は PnL額ではなく**確定足の価格水準到達**で行う(§A-2 準拠。
実装上は価格比較)。全手法に残る不変条件は **A-3(SL単調性=利益方向にのみ移動)** のみで、
建値化・トレールはこれを順守(`_advance_sl_to` が改善以外を no-op で無視)。

> **既知の留意点**: smc_bos の実測では早期建値化(`at_1r`)がむしろ成績を悪化させた
> 前例がある(smc_bos/spec.md §3.3)。本手法は仕様書どおり建値化+トレールを**既定・中核**
> として実装するが、実測(段階A4)で優位性を削る可能性がある。その場合の代替(トレール
> のみ/建値化なし等)は実測後に別途検討する。

## 5. プラットフォーム統合

- **L2 分析層** `provider.py`: `AtrTrendScalpProvider`(`SignalProvider` を構造的に充足)。
  EMA9/21・ATR14・出来高SMA20・平均ATR20(deque)・M15リサンプル→EMA50・押し目リング窓・
  単一ポジション・ミラー(`reset_position_mirror()` ウォームアップ・フック付き。smc_bos と同契約)。
- **L2 執行層** `execution.py`: `AtrTrendExecution`(`core.execution.ExecutionModel` を充足)。
  `market_tpsl`/`smc_bos` の成行執行を出発点に RUNNER 状態を1段追加。
- **L2 上位足** `resample.py`: `TfResampler`(M5→M15。`MacroResampler` と同型を自前実装。
  L2→L2 依存回避。将来 L1 昇格の余地)。
- **L2 語彙** `signals.py`: `AtrTrendPlan`(frozen。分割決済ジオメトリ tp1_int/
  trail_distance_ticks を明示。report_html 互換のため TradePlan 相当の中立フィールドも保持)/
  `AtrTrendOutput`。
- **レジストリ** `registry.py`: `StrategySpec(name="atr_trend_scalp", build, build_execution,
  report_spec)` を1件登録(既存登録は不変)。
- **必要インジケーター(L1)**: EMA/ATR/SMA すべて既存。**新設不要**。
- **`Timeframe`**: M5/M15 とも既存。**enum追加不要**(smc_bos の M30 追加より軽い)。

## 19. 約定現実性の修正: 現在値を越えるSLは成行決済(2026-11-15・**v1.1〜v1.3 の数値を下方修正**)

**発見**: トレールSL(`高値 − trail×ATR`)と TP1 後の建値SLは、確定足が高値から trail 幅以上
押して引けると**現在値(終値)より有利側**に置かれていた(買いなら終値より上)。現実のブローカーでは
そこに SL は置けず(MT5 は INVALID_STOPS で拒否)、置けたとしても即座に発動して現在値で約定する。
旧バックテスト(`SimBroker`)は `modify_sl` を検証せずに受け付け、次足で「SL価格ちょうど」で
約定させていたため、**現在値より有利な約定を計上**していた。v1.3 では TP1 後の 1,419件中
1,174件(83%)がこの経路で決済されていた。ライブでは同じ場面で `modify_sl` が拒否され、
`ORDER_ERROR` → キルスイッチで新規停止になっていたはずである(デモは発見時点で停止)。

**修正(`execution.py` `_protect_or_exit` / `provider.py` ミラー)**: SLの前進先が終値に達して
いる/越えている場合は、SLを置かずに**残玉をその足の終値で成行決済**する(`STOP_AT_MARKET`)。
バックテストとライブで同じ動きになる。TP2 到達の判定はトレールより先に行う(どちらも終値の
成行決済で約定は同じ。決済理由を TP2 として記録するため)。hypothesis プロパティ
`test_live_sl_never_at_or_beyond_bar_close` で「確定足処理後に残る建玉の SL は必ず終値より
不利側」を担保。`SimBroker`(depth50 と共用)は変更していない。

**修正後の実測(2021-06-14〜2026-11-13、`reports/atr_trend_scalp_v13_fixed_20261115/`、
`--strategy atr_trend_scalp_v13 --risk-pct 0.0003`)**:

## 20. MQL5 EA による独立検証(2026-11-15)

`mql5/AtrTrendScalp.mq5` に v1.3 の MQL5 独立実装(検証用 EA)を作成し、MT5 ストラテジーテスター
(Vantage Trading デモ、「リアルティックに基づいた全ティック」、2026-01-01〜11-14、0.02ロット)で実行した。

**シグナルの一致**: EA 288件 / Python 279件のエントリーのうち **278件が同じ足・同じ方向**で一致
(残りは数件の境界差)。エントリー判定ロジックの移植は正しいことを確認した。

**成績の差**: 同期間で EA は PF 0.98・−$25.41、Python(修正後 §19)は PF 1.132・+$155.60。
共通 278件の損益は Python +$138.21 に対し EA +$20.20。スワップ・手数料はいずれも $0
(最長保有 25分)。差の主因は**スプレッド**: Python の CLI バックテストは `LedgerBroker(spread_ticks=2)`
固定だが、ブローカーの実スプレッド(2026年の M5 足 `spread` 列)は**中央値 26 ティック**
(p25 23 / p95 26)。Python を spread=20 で回すと 2026 年は PF 0.998 となり EA とほぼ一致した。
また Vantage の XAUUSD は `trade_stops_level=20`(現在値から 20 ティック以内に SL を置けない)。

**実スプレッド(26ティック)での全期間(Python・修正後 v1.3)**: 2,706件 / **PF 0.802** / 純益 −$1,154.80。
年次 PF 2021 0.51 / 2022 0.61 / 2023 0.72 / 2024 0.73 / 2025 1.12 / 2026 0.96。
**本手法(1トレードの平均利幅が ATR の数十%しかないスキャルピング)は、このブローカーの取引コストを
吸収できない。** v1.0〜v1.3 の採否判断はすべてスプレッド 2 ティックの前提で行われており無効。
(参考: 2021〜2025 年の実スプレッドは未取得。2026 年と同水準と仮定した概算)

**プラットフォーム全体への含意**: `main.py` のバックテストは全手法でスプレッド 2 ティック固定。
depth50 も同じ前提で、往復 +24 ティック×ステップの概算では黄金値期間の PF 1.487 → 約 1.37。
depth50 の黄金値(ビット一致の回帰基準)は「実装が変わっていないこと」の検証値としては有効だが、
「実力値」としては実スプレッドで別途評価し直す必要がある。
