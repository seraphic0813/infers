# /dev-pipeline

新パラメータ・新フィルタ・新手法変更を評価するときの標準パイプライン。
改善プラン T17(開発サブエージェント・パイプラインの定型化)の実装。
改善レポート §6「開発時 Agentic 化」の「最適化→アナリスト→インバリアント・
レビュアー→/bit-check」の直列構成をそのまま手順書化したもの。

**このパイプラインはトレード判断のホットパスに一切関与しない**(開発プロセスの
定型化であり、`provider.py`/`execution.py`/`engine.py` 等のコードには触れない)。

## 全体像(直列・4段)

```
① 実験 (/sweep)
     ↓ 採否基準を事前宣言済みで完走
② 年次分解 (/annual-breakdown)
     ↓ 警告なし、または警告の意味を吟味した上で採否基準に照らして判断可能
③ インバリアント・レビュー (.claude/review-checklist.md)
     ↓ A不変条件・B契約(該当する場合)に違反なし
④ 完了ゲート (/bit-check)
     ↓ PASS
完了・コミット
```

**直列専用・並列多重化しない**(再現性優先)。同時に複数の実験候補を並行して走らせ、
後から良い結果だけを拾う運用はしない(過剰適合の温床になる。CLAUDE.md 定石6と
同じ理由)。1回のパイプライン実行につき、評価対象は1構成(または `/sweep` の
1スイープ計画)に限定する。

---

## ① 実験(`/sweep`)

- **入力**: 対象手法(登録済み `--strategy` 名 or `--provider-class`)、掃引する
  パラメータと候補値、**採否基準**。
- **必須事前作業**: 採否基準(例:「全暦年 PF>1.2 かつ買い側黒字」)を実験実行**前**に
  文字で書き出す(コミットメッセージ・spec.md・issueなど残る場所に)。基準の文言は
  この段階で固定し、以降のどの段階でも変更しない(定石6「採否基準の事後変更禁止」)。
- **実行**: `/sweep` Skill(`tools/sweep.py`)。ベースラインのビット一致自己検証
  (`--golden-*` 指定時)が内蔵されているため、まず既定パラメータでの自己検証が
  通ることを確認する。
- **次へ進める条件**: スイープが異常終了せず、各候補構成の結果(トレード数・PF・
  DD・勝率)が出力されていること。この段階では「良い数値が出た」ことは次段階へ
  進む条件ではない(年次分解を経ていない全期間PFだけでの判断は禁止)。

## ② 年次分解(`/annual-breakdown`)

- **入力**: ①で生成された各候補の `reports/<name>/report_data.js`(`/sweep` は
  自動的に年次分解を適用するが、単体の `--report` 出力に対して個別に走らせる場合は
  このコマンドを直接使う)。
- **実行**: `/annual-breakdown` Skill(`tools/annual_breakdown.py`)。
  (a) 単年純益寄与>50%、(b) いずれかの暦年PF<0.9、の2警告を機械的に検出する。
- **次へ進める条件**: 警告が**発火していない**こと。**警告が1件でも発火した候補は
  ③④へ進めず、その時点で不採用(または「参考記録」としてレジストリ残置のみ)と
  結論づける。** 警告が出た構成を「他の指標が良いから」という理由で次段階へ通す
  ことは禁止(smc_bos の頻度レバー実験・narrow_focus_mtf で確認済みの過剰適合
  パターンを繰り返さないため)。

## ③ インバリアント・レビュー(`.claude/review-checklist.md`)

- **入力**: ①②を通過した候補のコード差分(provider/execution/registry等)。
- **実行**: `.claude/review-checklist.md` の該当観点(A-2/A-3/A-5〜A-10、
  narrow_focus 変更なら B契約・depth50不可侵も)を差分に対して機械的に検査する。
- **次へ進める条件**: 全観点で違反なし。違反が見つかった場合は実装へ差し戻し、
  ①からではなく実装修正後に③から再開してよい(①②の実験結果自体は変わらない
  ため。ただしコード修正がロジックに影響する場合は①からやり直す)。

## ④ 完了ゲート(`/bit-check`)

- **入力**: ③を通過したコード(narrow_focus・core・execution に触れていない
  新手法追加が大半だが、触れる変更の場合は特に重要)。
- **実行**: `/bit-check` Skill(`tools/bit_check.py`)。pytest 全合格 +
  depth50 再現バックテストの**強い一致**(トレード列+AIゲート統計)。
- **次へ進める条件**: PASS。**PASSしなければコミットしない**(CLAUDE.md「完了
  ゲート」節)。FAILした場合は原因を特定して差し戻す(黄金値を後から書き換えて
  通すことは禁止)。

**④がPASSして初めてコミット可能**。コミットメッセージには、①で宣言した採否基準と
②の年次分解結果(採用/不採用の判定根拠)を残す。

## 実例: T16 `narrow_focus_mtf`(2026-07、不採用判定)

直近の実施例。手順どおりに①→②で不採用が確定し、③④まで進まなかったケース
(パイプラインが「早期に安全に止まる」ことを示す好例)。

1. **① 実験**: H1判定足+D1マクロの新変種(`narrow_focus_mtf`)を実装。
   **採否基準を実装前に宣言**: 「全暦年 PF>1.2 かつ買い側黒字」
   (`src/infers/strategies/narrow_focus/mtf-variant.md` §1)。
   実測: 80トレード / 全期間PF 0.670338236 / 純益 −$418.71。
2. **② 年次分解**: `/annual-breakdown` で暦年PF<0.9が4年
   (2021=0.000・2022=0.720・2025=0.126・2026=0.000)発火。買い側単独もPF0.421で赤字。
   → **事前宣言した採否基準(全暦年PF>1.2 かつ買い側黒字)に両方未達**。
3. **判定**: **不採用(参考記録)**。レジストリ登録は残置(コストなし)、ライブ投入
   はしない。③のインバリアント・レビュー、④の `/bit-check` は形式的には実行可能
   だが(depth50を変更していないため)、②で不採用が確定した時点でこの実験自体の
   採用可否には意味を持たない(手法自体は登録済みコードとして残るため④は通常運用の
   一部として別途実行される)。
4. **主要知見**(参考): 売り偏重(86.25%)はTF構造では解消しない、BE到達率
   11.25%(depth50=47.6%)でH1較正不整合が利確を阻害、トレードスパンは
   depth50比10〜12倍に伸びたが原典意図の数日〜週にはなお未達。

詳細は `src/infers/strategies/narrow_focus/mtf-variant.md` §1・§4、
`reports/README.md`、`docs/improvement-plan-2026-07.md` T16 節を参照。

## 禁止事項(過剰適合の人間側対策)

- **採否基準の事後変更禁止**: ①で宣言した基準を、②以降の結果を見てから
  緩めたり厳しくしたりしない。基準そのものを見直したい場合は、今回の実験を
  いったん不採用として結論づけた上で、次の実験サイクルとして新基準を再宣言する。
- **並列多重化しない**: 複数パラメータ候補・複数手法変種を同時並行で走らせて
  結果の良いものだけ拾う、という運用はしない。1パイプライン=1評価対象。
  複数候補を比較したい場合は `/sweep` の中(単一パイプラインの①内)で完結させる。
- **全期間1本の指標での判断禁止**: ②を経ない全期間PF・純益だけでの採用判断は
  禁止(CLAUDE.md 定石6)。
